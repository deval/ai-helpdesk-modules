Module 1 · 09:00–10:00

What is an LLM?

Not a database — it doesn't "look up" answers.

A statistical next-token predictor, trained on text, predicting the most likely next token.

No internal fact-checker, no concept of "I don't know this."

An LLM optimizes for plausible, not true.

Module 1

How this helps a helpdesk

Good at transforming text it's already given:

  • Drafting a reply in a consistent tone
  • Summarizing a long thread
  • Classifying a ticket into a category
  • Answering when the answer is fully in the text handed to it

This is why grounding works — you're not asking it to recall, you're asking it to transform what you gave it.

Module 1

The risk this creates

Asked something outside what it was given, it doesn't default to "I don't have this info."

It keeps predicting plausible text → a confident, fluent, wrong answer.

For a helpdesk: a wrong answer delivered confidently is harder to catch than one that's obviously uncertain.

Module 1

Three levels of AI in support

Ticket deflection customer never reaches a human

Agent-assist AI drafts, human approves — safest place to start

Full automation AI acts with no human step — narrow, high-confidence only

Most of this workshop lives in agent-assist — the "draft → hold for review" pattern.

Module 1

Reference numbers (approximate)

AI-assisted deflection: commonly reported 20–40% for well-scoped FAQ categories.

Agent-assist drafting: reported to cut handle time 10–30% when agents edit rather than write from scratch.

Treat as sanity-check ranges, not promises — vendor deflection numbers often don't hold on a real messy queue.

Module 2 · 10:15–11:30

Tokens & context window

A token ≈ ¾ of an English word.

Gemini 2.5 Flash free tier: 1M-token window (~750,000 words) — plenty for a pasted knowledge file plus a ticket.

Module 2

Hallucination

Fluent, confident, wrong text when the model isn't given the facts and is asked something requiring them.

It doesn't "know" it's guessing.

The fix: grounding — give it the source text, and instruct it to only use that.

Module 2

Anatomy of a support-reply prompt

  1. Role — who the model is acting as
  2. Rules/constraints — hard boundaries
  3. Reference facts — the grounding
  4. The input — the ticket itself
  5. Output format — plain text or structured JSON
Lab 1.0 · Prompt-tuning sprint

Setup (5 min)

  • console.groq.com → Playground
  • Model: openai/gpt-oss-120b
  • Confirm you can send a message and get a response

Round 1: naive prompt (10 min) · Round 2: pair up and break each other's prompts (15 min) · Round 3: group diagnosis (15 min)

Lab 1.0 · Worked example

Watch hallucination happen live

Naive prompt:

Reply to this customer complaint politely.
Fails: "I've issued a full refund of $[amount]..."
— invents a refund amount and a policy decision no one made, ignores the tracking complaint.
Lab 1.0 · Worked example

Fix it: grounding

Improved prompt — rules + reference facts:

Rules: - Only state facts present in the ticket or policy notes - Do NOT promise a refund amount - Acknowledge the specific complaint - Tone: warm, concise, max 120 words Policy notes: - Orders >5 days late qualify for refund review, not automatic refund - Tracking issues get escalated to logistics within 1 business day
Result: acknowledges both issues, states refund review (not a promised amount), commits to logistics escalation.
No invented facts.

Module 4 · 14:00–16:30

Retrieval-quality issues

Source granularity — one giant PDF with no headings retrieves worse than the same content split into sections.

Contradictions across sources — NotebookLM cites both; it's on you to spot the conflict.

Real production failure modes, not just lab exercises.

Channels in & out

Generic Webhook (any system that POSTs JSON) and Telegram (real chat channel).

Calling an LLM from n8n

Lab 2.2 · Classify & score

Pipeline

  1. Manual Trigger → Set (sample ticket) → HTTP Request (classify prompt)
  2. Code node: parse JSON string → real fields
  3. Switch on category (billing/technical/general)
  4. IF: urgency == high AND sentiment == negative → needs-review branch
Module 8 · 14:45–16:30

Drafting replies automatically

Same HTTP Request pattern — but drafts a reply and writes it to a place a human checks first.

Lab 2.3 · Draft-and-hold

Review-queue record

  • Write to Sheets/Telegram/CSV/Postgres — this is your review queue

Module 10 · 10:45–12:00

Guardrails & escalation logic

Model confidence alone is a weak signal — models are often confidently wrong.

Pair it with deterministic checks: keyword tripwires for refunds, legal, safety, cancellation.

Lab 3.1 · Guardrail branch

The OR condition

confidence != "HIGH" OR body contains: refund, cancel, lawsuit, legal, chargeback

True → escalate to review queue

False → auto-approved (logged, not actually sent in the lab)

Test: high-confidence-but-flagged-keyword MUST still escalate — that's the point of the OR.

Module 11 · 13:00–14:00

Metrics that matter

  • Deflection rate = auto-approved ÷ total
  • Escalation rate — by category; >80% signals a coverage gap, not "unautomatable"
  • Time-to-first-response — ticket-in to draft-ready
  • CSAT delta — needs weeks of real volume, not visible in 3 days
Module 11 · Privacy

Before any real rollout

Strip or mask PII before it goes into any third-party API call.

Gemini's free tier: prompts/responses may train Google's models.

Production rollout → paid tier with a no-training-data agreement.

Module 11 · Rollout, phased

Three phases

  1. Shadow mode — AI drafts, human writes independently, compare only. Zero customer risk.
  2. Co-pilot mode — human reviews/edits before sending. Runs until numbers are trusted.
  3. Narrow auto-send — one low-risk category, tripwires reviewed by policy owner.

Capstone — Build your team's agent

  • NotebookLM knowledge base for one real product/policy area
  • n8n: intake → classify → grounded draft → guardrail → send/escalate
  • One escalation rule specific to your own risk area
  • 5-minute live demo + one-page rollout plan
